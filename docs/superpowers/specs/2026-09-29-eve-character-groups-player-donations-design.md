# EVE 角色组与玩家转账收入设计规格

日期：2026-09-29  
状态：已获用户批准

## 背景与目标

现有应用把全部已授权角色视为一个扁平列表，报表仅统计赏金、ESS 和任务相关收入及税费。用户需要把角色组织成具名角色组，并以角色组为同步和报表边界。每个已授权角色最多属于一个组；新角色先进入“未分组”。

收入统计新增 ESI 钱包流水类型 `player_donation`。来自组外角色的正向转账计入总收入，但在类型分项和流水明细中单独显示为“玩家转账”；同一角色组内的角色相互转账不计收入，避免在组内搬运 ISK 时虚增收益。

成功标准：

- 用户可以创建、重命名和删除具名角色组。
- 用户可以把已授权角色加入一个组、换组或移回未分组，且角色不能同时属于多个组。
- 报表和手动同步始终绑定一个明确的角色组。
- 外部正向 `player_donation` 计入到账收入和税后收入，并单独显示明细分类。
- 组内互转无论角色是否启用、是否在当前报表中被勾选，都不会进入任何收入合计或明细。
- 升级保留现有角色、授权、统计起点和全部钱包历史。

## 范围与非目标

本次范围包括角色组持久化、成员管理、按组同步、按组报表、`player_donation` 分类、相关界面和文档。

本次不包括：

- `player_trading`、市场交易、合同或物品估值收入。
- 一个角色同时加入多个组。
- 跨组总报表或多组联合同步。
- 删除角色、授权或历史流水。
- 修改现有 EVE SSO 权限；仍只使用 `esi-wallet.read_character_wallet.v1`。

## 方案选择

采用一对多关系：新增 `character_groups` 表，并在 `characters` 表增加可空 `group_id` 外键。

未采用独立成员关系表，因为当前规则明确要求一个角色只能属于一个组；额外联表不会带来现阶段收益。未采用配置文件或浏览器本地存储，因为它们无法提供可靠的数据库约束、事务和迁移能力。

## 数据模型与迁移

数据库架构版本从 1 升至 2。

### `character_groups`

- `group_id INTEGER PRIMARY KEY`
- `name TEXT NOT NULL COLLATE NOCASE UNIQUE`
- `created_at TEXT NOT NULL`，保存带时区的 UTC ISO 时间

组名在应用层去除首尾空格后校验，长度必须为 1–50 个字符。唯一约束同时阻止仅拉丁字母大小写不同的重复名称。

### `characters`

新增：

- `group_id INTEGER NULL REFERENCES character_groups(group_id) ON DELETE SET NULL`

可空外键同时表达“未分组”和单组归属。`CharacterRecord` 增加 `group_id: int | None`，并新增只读的 `CharacterGroupRecord` 模型。

### 迁移规则

- 新数据库直接创建版本 2 的完整结构。
- 版本 1 数据库先创建 `character_groups`，再为 `characters` 增加可空外键列，最后把 `PRAGMA user_version` 更新为 2。
- 所有现有角色迁移后保持未分组；钱包流水表不重写。
- 迁移在单一事务中完成。发生错误时回滚，不能留下已改结构但版本号未更新的状态。
- 初始化继续保持幂等；高于应用支持版本的数据库应明确拒绝，而不是尝试降级。

删除组在事务中完成：先把该组成员的 `group_id` 设为 `NULL`，再删除组。角色、加密刷新令牌、统计起点、启用状态和钱包流水全部保留。外键的 `ON DELETE SET NULL` 作为数据库层的第二道保护。

## 仓储与服务边界

新增 `CharacterGroupRepository`，负责：

- 列出、按 ID 获取、创建、重命名和删除组。
- 校验规范化后的唯一组名。
- 在删除时原子地把成员移回未分组。

扩展 `CharacterRepository`，负责：

- 列出某组的全部角色或全部未分组角色。
- 把一个已存在角色分配给某个已存在组，或把它移回未分组。
- 通过 `characters.group_id` 的单值列保证一个角色最多属于一个组。

重新授权已有角色时不得覆盖其 `group_id`。新授权角色的 `group_id` 为 `NULL`。保留现有的首次授权后单角色自动同步：该数据在角色分组前不会出现在任何组报表中；后续界面上的手动同步严格按当前组执行。

`SyncService` 新增按组入口。它只遍历指定组内启用的角色，并继续逐角色顺序同步、隔离失败和保留旧报表。未分组角色及其他组角色不参与本次手动同步。

## 转账分类规则

现有四种收入和五种税费规则保持不变。收入分类顺序新增：

1. 赏金
2. ESS
3. 任务奖励
4. 任务限时奖励
5. 玩家转账

只有满足以下全部条件的流水才分类为“玩家转账”收入：

- `ref_type == player_donation`
- `amount > 0`
- 能从 `first_party_id` 和 `second_party_id` 中确定至少一个不同于当前 `entry.character_id` 的交易对方
- 所有已确定的交易对方均不属于当前角色组

若任一交易对方 ID 属于当前组，则整条流水判定为组内互转并排除。该判断使用角色组的完整成员 ID 集合，包括停用角色以及当前报表未勾选的角色，确保筛选或启停不会改变同一流水的业务性质。

如果 `player_donation` 缺少可识别的交易对方，应用无法证明它来自组外，因此保守地不计收入，并记录不含敏感内容的未知格式日志。负数和零金额 `player_donation` 不属于收入。`player_trading` 继续忽略。

分类函数需要显式接收角色组完整成员集合，避免依赖全局状态。仪表盘构建和流水 API 必须使用同一分类入口，防止总额与明细口径漂移。

## 报表口径

报表请求必须带一个有效 `group_id`。角色组的完整成员集合用于转账内外部判断；实际汇总集合按以下规则确定：

- 未提供 `character_id` 时，汇总该组全部启用角色。
- 提供一个或多个 `character_id` 时，只汇总这些角色；每个 ID 必须属于该组，停用角色可以被显式选择。
- 其他组或未分组角色出现在筛选参数中时返回 400，不静默忽略。

顶部“到账收入”、每日趋势和每日账本继续显示合计收入，即现有刷怪/任务收入加外部玩家转账。类型分项单独显示“玩家转账”；其税费为零，净收入等于转入金额。流水明细把外部转账标为“玩家转账”。组内互转不出现在总额、趋势、类型分项、角色分项或已纳入流水明细中。

## HTTP API

所有读取接口继续要求已登录查看者；所有修改接口继续要求已登录查看者及匹配的 CSRF 令牌。

### 角色组

- `GET /api/groups`：返回按创建顺序排列的组、成员数量，以及用于界面展示的未分组角色数量。
- `POST /api/groups`，JSON `{name: xxx}`：创建组。
- `PATCH /api/groups/{group_id}`，JSON `{name: 新名称}`：重命名组。
- `DELETE /api/groups/{group_id}`：删除组并把成员移回未分组；返回被移动的角色 ID，便于前端刷新状态。

### 角色成员关系

- `GET /api/characters`：在现有公开字段上增加 `group_id`，不得暴露刷新令牌。
- `POST /api/characters/{character_id}/group`，JSON `{group_id: 123}`：加入或换到指定组。
- 同一接口传 `{group_id: null}`：移回未分组。

### 报表与同步

- `GET /api/dashboard?group_id=<id>&from=...&to=...&character_id=...`
- `GET /api/entries?group_id=<id>&from=...&to=...&character_id=...`
- `POST /api/sync?group_id=<id>`

缺失或格式错误的组 ID、无效日期、重复组名和跨组角色筛选返回稳定的 400/404 中文错误。数据库冲突不得把 SQLite 异常文本回显给浏览器。同步继续返回逐角色结果；单个角色失败不撤销同组其他角色已完成的同步。

## 界面与交互

界面保留现有“EVE 舰长个人账本”的视觉方向和主要报表结构，不进行无关重做。

左侧控制栏顶部增加当前角色组选择器，以及创建、重命名和删除操作。组操作使用清晰的内联表单或对话框，保持键盘可用、焦点可见，并给出明确成功或失败状态。

当前组区域显示：

- 组内成员的报表勾选项、同步状态和启停按钮。
- 把成员移回未分组的操作。
- 当前组专用的“同步钱包流水”按钮。

未分组区域显示所有尚未归组的已授权角色，并允许把角色加入当前组。角色换组属于显式操作；不会因为用户当前浏览某个组而自动归组。

空状态必须提供下一步：

- 没有任何组时，引导创建第一个角色组。
- 当前组没有成员时，引导从未分组角色中添加。
- 没有可同步的启用成员时，说明需要添加或启用角色。

报表标题显示当前组名。类型分项增加独立的“玩家转账”，但顶部到账收入和每日数据仍显示合计。删除组前明确提示“角色与历史流水会保留并移回未分组”。

## 错误处理与安全

- 组和成员修改使用数据库事务；失败时不产生部分状态。
- 所有 ID 参数只接受正整数；JSON 由严格模型校验，忽略或回显敏感值均不允许。
- 新接口沿用现有会话认证、CSRF 和安全错误转换。
- `player_donation` 的 `reason` 和 `description` 仍是私人钱包数据，只在已认证的本地界面展示，不写入错误信息。
- 角色组不改变 OAuth scope，也不增加写入 EVE 的能力。

## 测试策略

按测试驱动方式实施，至少覆盖：

### 存储与迁移

- 全新数据库建立版本 2 结构并启用外键。
- 真实版本 1 结构升级后保留角色、令牌、统计起点和钱包流水，角色均为未分组。
- 初始化幂等，迁移失败回滚，不支持的未来版本被拒绝。
- 创建、重命名、去空格、空名、超长名和重复名。
- 一个角色加入、换组、移回未分组；未知组或角色失败。
- 删除组后成员未分组且全部历史保留。

### 分类与报表

- 外部正向 `player_donation` 分类为“玩家转账”并进入总收入。
- 组内互转被排除，包括发送方停用、发送方未被当前报表勾选的情况。
- 跨组转账对接收方所在组仍属于外部转账。
- 零或负数 `player_donation`、`player_trading` 和缺失交易对方均不计收入。
- 类型分项分开显示，顶部、每日和角色合计保持精确 Decimal 结果。

### 同步与 Web

- 手动同步只处理当前组内启用角色，并保持逐角色失败隔离。
- 组 CRUD、成员变更、报表和同步接口的认证、CSRF、参数和安全错误。
- 缺少组、未知组及跨组角色筛选被拒绝。
- 前端包含角色组选择、空状态、成员管理、确认文案和“玩家转账”分类。
- 现有 SSO、同步、报表和安全测试继续通过。

完成前运行完整 pytest、Ruff、`git diff --check`，并检查源 `main` 工作目录没有被修改。

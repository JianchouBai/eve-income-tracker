# EVE Income Tracker v1.0.0 可配置数据目录设计规格

日期：2026-09-30
状态：待用户书面确认

## 背景与目标

当前 Windows 桌面版把数据库、密钥、日志、备份和 WebView 用户数据固定保存在 `%LOCALAPPDATA%\EVE Income Tracker`。这能安全支持覆盖升级，但不能满足用户把持续增长的数据放到 D 盘或其他磁盘的需求；首次启动的“导入数据库”提示也容易让全新安装用户误以为必须先找到数据库文件。

本次目标是将桌面版发布为首个正式版本 **v1.0.0**，并允许用户在首次启动或之后的设置页中选择数据存储位置。迁移必须在验证成功后才切换，任何失败都不能损坏原数据或悄悄创建第二套空数据库。

成功标准：

- 数据库、DPAPI 保护的本机密钥、日志、备份和 WebView 用户数据都可放在用户选择的非系统盘。
- 每台电脑继续拥有独立的数据目录、数据库和授权，不增加跨设备同步。
- 已有 `%LOCALAPPDATA%` 数据可自动迁移；从任意自定义盘迁往另一个盘时使用同一流程。
- 数据盘暂时不可用时停止启动并提示处理，不回退到默认目录，也不创建空数据库。
- 设置页可查看占用、打开目录、删除迁移恢复副本并发起再次迁移。
- 覆盖升级和默认卸载保留数据位置；重新安装可自动接回原数据库。
- 数据始终位于 Git 仓库之外，不会被提交或推送到远端仓库。

## 范围与非目标

范围包括数据位置注册表、路径解析、数据目录安全标记、首次启动向导、原生目录选择、迁移和回滚、设置页、启动错误处理、升级与卸载行为、版本号以及自动化和人工验证。

不包括：

- 将数据直接放在 EXE 旁边的便携模式。
- 两台电脑之间复制、同步或合并数据库。
- 移动由 Windows 管理的 Microsoft WebView2 Runtime；仅移动本应用的 WebView 用户数据。
- 云备份、自动更新或新版数据库格式设计。
- 在数据盘丢失时自动新建数据库；新建空数据必须是未来单独设计的显式恢复操作。

## 方案选择

采用 **HKCU 注册表路径指针 + 应用管理的数据根目录 + 启动前事务式迁移**。

注册表适合让应用、升级安装器和卸载器共同读取同一位置，也不会因为程序覆盖安装而丢失。它只保存很小的路径和迁移状态，不保存钱包数据或令牌。

未采用 `%LOCALAPPDATA%` JSON 指针文件，因为安装器解析和保留它更复杂，文件丢失后也更难重新连接。未采用 EXE 同目录存储，因为安装目录应按只读处理，且升级、权限和卸载边界更危险。

## 版本规则

- 当前 `0.1.0` 在实现完成后升级为语义版本 `1.0.0`。
- `app/version.py` 中的 `APP_VERSION` 继续作为唯一版本来源。
- Python 包、EXE 元数据、安装器和安装包文件名使用 `1.0.0`。
- 界面主标识可简写为 `V1.0`，“关于”页面显示完整的 `V1.0.0`。
- 正式发布的 Git 标签使用 `v1.0.0`；安装包名为 `EVE-Income-Tracker-1.0.0-x64-Setup.exe`。
- 安装包仍作为 GitHub Release 附件发布，不提交到 Git 仓库。

## 数据位置模型

安装版在以下当前用户注册表项保存状态：

`HKEY_CURRENT_USER\Software\JianchouBai\EVE Income Tracker`

至少包含：

- `DataRoot`：当前数据根目录的规范化绝对路径。
- `DataRootId`：与当前目录安全标记一致的随机数据根 ID。
- `DataRootSchema`：路径和标记协议版本，首版为 `1`。
- `PendingMigrationTarget`：设置页已确认但尚未执行的目标父目录；正常状态下不存在。
- `PendingCleanupRoot`：迁移成功但尚未清理完成的原数据目录；正常状态下不存在。
- `PendingCleanupRootId`：与待清理原目录安全标记一致的随机数据根 ID。

用户在首次启动或设置页选择的是父目录。程序在其中创建 `EVE Income Tracker` 子目录，并在确认前展示最终完整路径。例如选择 `D:\` 后使用：

```text
D:\EVE Income Tracker\
├─ data\eve_income.sqlite3
├─ config\local.key
├─ config\webview\
├─ logs\
├─ backups\
└─ .eve-income-tracker-data.json
```

安全标记包含固定应用标识、标记模式版本、随机数据根 ID 和创建时间。路径服务集中负责注册表读写、路径规范化和目录验证，业务模块只消费解析后的 `AppPaths`，不直接读取注册表。

开发源码模式继续使用项目现有开发路径或显式测试覆盖，不读取真实用户注册表。打包冒烟测试继续使用隔离的临时目录。

## 启动与首次运行

桌面启动顺序调整为：

1. 获取单实例互斥量。
2. 读取并验证注册表数据位置。
3. 执行待处理迁移或清理任务。
4. 解析资源和数据路径，配置日志。
5. 初始化密钥、数据库、本地服务和 WebView。

如果 `DataRoot` 存在且标记有效，程序直接使用该目录。如果磁盘离线、路径不存在、标记不符或目录不可读写，程序在打开数据库前停止，并提供“重试”“定位已有数据目录”“退出”。“定位”只接受带有效标记且数据库可验证的现有目录，不能创建空数据库。

注册表尚无 `DataRoot` 时：

- 如果检测到旧版精确目录 `%LOCALAPPDATA%\EVE Income Tracker` 及已知数据布局，向用户说明发现已有数据，并让用户选择保留原位置或迁移到新的父目录。旧目录没有安全标记时，在用户确认后先验证已知布局并补写标记；这是迁移提交点前唯一允许写入原目录的元数据，不更改数据库、密钥或其他用户数据。
- 如果没有现有数据，首次启动向导提供默认位置和自定义位置，并显示最终路径。
- 用户确定空数据根后，才显示“导入旧版数据库（可选）”；界面明确提供“跳过并新建数据库”，不再让导入看起来是必填步骤。
- 用户选择继续使用现有默认目录时，为它补写安全标记和注册表路径，不复制数据。

## 组件边界

新增或扩展以下独立组件：

- `DataLocationStore`：封装 HKCU 注册表读写，可用内存实现进行跨平台单元测试。
- `DataRootValidator`：规范化路径，验证安全标记、目录结构、权限、目标空闲状态和禁止删除的宽泛路径。
- `DataMigrationService`：生成迁移计划、估算空间、复制、校验、切换、回滚和安排清理，不依赖 UI。
- `RecoverySnapshotService`：创建、列出、删除和按保留策略清理迁移恢复副本。
- `NativeFolderPicker`：只负责选择父目录或定位已有数据根，不承担路径信任判断。
- `DataLocationController`：为首次启动和设置页编排上述组件，返回可展示的阶段与错误。

现有 `resolve_app_paths` 接收已经选定的数据根，而不是自行假定 `%LOCALAPPDATA%`。桌面启动器负责在数据库、日志和 WebView 打开前完成位置解析和迁移。Web、存储和 ESI 业务层不依赖 Windows 注册表或原生对话框。

## 迁移流程

迁移必须持有单实例锁，并在数据库、本地服务和 WebView 未打开时执行。设置页发起迁移时先写入 `PendingMigrationTarget`，然后安全关闭窗口和服务，由桌面启动循环在重新初始化前执行迁移。

迁移步骤：

1. 解析原数据目录与目标父目录，拒绝相同路径、磁盘根目录、系统目录、程序安装目录及其他宽泛或危险目标。
2. 目标正式目录必须不存在或为空；已有有效应用数据的目录只能通过“定位已有数据”连接，不能作为覆盖目标。
3. 估算完整复制量和可选恢复副本大小，验证目标空间和写权限。
4. 在目标父目录创建带随机迁移 ID 的临时目录，并先写入未完成状态的安全标记。
5. 复制数据库、密钥、配置、日志、备份和 WebView 用户数据。数据库及其 WAL 状态在关闭写入后以 SQLite 安全方式生成一致副本。
6. 校验文件清单和大小、密钥可读性、数据库支持版本与 SQLite 完整性；再将标记改为完成状态。
7. 如果用户保留默认选项，在目标 `backups` 中创建一份迁移恢复副本。
8. 在同一目标卷内将临时目录重命名为正式目录，随后更新 `DataRoot`。注册表切换是提交点，在此之前原数据目录保持不变。
9. 使用新路径重新打开密钥和数据库。失败时把注册表恢复为原路径，保留原数据并隔离失败目标以供诊断。
10. 新位置验证成功后，清理迁移前的**原数据目录**，不对盘符作任何假设。清理前再次验证原路径、安全标记和数据根 ID。

如果原目录因文件占用未能清理，迁移仍视为数据切换成功；程序记录 `PendingCleanupRoot` 和 `PendingCleanupRootId`、显示完整遗留路径，并在下次启动安全重试。清理只能删除经过验证的准确数据根，不得删除其父目录、磁盘根目录、用户目录或跟随意外的重解析点。

任何提交点之前的失败都会清理临时目录并继续使用原数据。除为旧版精确默认目录补写安全标记外，目标不可用、空间不足、文件复制失败、校验失败或注册表写入失败都不得修改或删除原数据。

## 迁移恢复副本

迁移恢复副本是清理原目录后的短期保险，只包含：

- `eve_income.sqlite3` 的一致副本；
- `local.key`；
- 恢复数据库和授权所需的必要配置。

它不重复保存 WebView 缓存、普通日志或其他非关键文件。迁移界面在确认前分别显示数据迁移预计占用、恢复副本预计占用和目标可用空间。用户可以明确取消勾选“不创建恢复副本”，但默认创建。

恢复副本使用压缩归档，最多保留一份。仅当新位置已连续成功启动至少三次且副本已满七天时自动删除。设置页显示其创建时间和实际大小，并提供“立即删除”操作。副本与正式数据位于目标盘，因此不会继续占用原数据盘空间。

## 设置页面与交互

设置页新增“数据存储”区域，显示当前完整路径、卷、各类别占用和总占用。提供：

- “打开数据目录”；
- “更改存储位置”；
- “删除迁移恢复副本”（存在时）；
- 恢复副本默认选项和保留说明。

“更改存储位置”调用受限的原生目录选择器。确认页显示最终目录、迁移量、恢复副本量、剩余空间和原目录清理说明。提交后界面说明程序将重启迁移；桌面启动器安全关闭服务，在重启阶段显示当前进度，成功后重新打开主窗口。

目录选择返回值始终由后端重新规范化和验证。只有桌面会话可以访问数据位置接口，修改请求继续要求签名会话和 CSRF；普通浏览器开发模式不暴露原生文件系统能力。

## 安装、升级、重装与卸载

程序安装目录和数据目录相互独立。首次安装可在安装器中选择程序目录；数据目录由首次启动向导选择。覆盖升级只替换程序文件，不修改 `DataRoot`、数据安全标记或个人数据。

重新安装时，如果保留的注册表路径及数据标记有效，程序自动接回原数据库。如果路径不可用，按启动错误流程要求重试或定位已有数据，不创建空库。

卸载默认保留数据和位置注册表，以便重装继续使用。用户明确选择删除个人数据时：

1. 卸载器从注册表读取当前 `DataRoot`，显示规范化完整路径并二次确认。
2. 同时验证固定应用标识、安全标记、注册表 `DataRootId`、路径边界和危险目录黑名单。
3. 验证失败时拒绝删除并保留注册表；静默卸载始终保留个人数据。
4. 仅在数据目录删除成功后删除数据位置注册表。
5. 若删除不完整，显示遗留路径并保留位置记录，方便人工处理。

Microsoft WebView2 Runtime 是 Windows 共享组件，不随应用数据迁移，也不由本应用卸载。`config\webview` 中属于本应用的用户数据随数据根迁移和删除。

## 错误处理与安全

所有迁移错误提供发生阶段、原路径、目标路径和可执行的下一步，但日志和界面不得显示令牌、密钥内容或钱包隐私数据。

关键规则：

- 路径不可用时失败关闭，不回退到 `%LOCALAPPDATA%`。
- 注册表切换前原数据不可修改或删除。
- 数据库完整性、支持版本或密钥检查失败时不得提交迁移。
- 目标非空时不得合并或覆盖。
- 清理必须验证安全标记和数据根 ID，并使用规范化后的准确路径。
- `local.key` 仍由 Windows DPAPI 当前用户保护；同一 Windows 用户跨磁盘移动可用，复制到另一台电脑不作为迁移或同步方案。
- 所有注册表和文件操作错误都转为中文可操作提示，不能让未处理异常直接结束程序。

## 测试策略

自动化测试至少覆盖：

- 注册表存储的创建、读取、保留、损坏值和内存替身。
- 默认目录、自定义盘、开发模式和打包冒烟模式的路径解析。
- 安全标记创建、版本、随机根 ID、伪造或缺失标记及危险路径拒绝。
- 首次空安装、旧 `%LOCALAPPDATA%` 数据发现、保留原位和迁移选择。
- 完整迁移成功，以及复制、空间、哈希、SQLite、密钥、重命名、注册表和重新打开各阶段失败时的回滚。
- 从 C 到 D、D 到 E 和同卷不同目录迁移，不在测试逻辑中写死原盘符。
- WAL 数据一致性、目标非空拒绝、重复迁移恢复和遗留临时目录处理。
- 原目录清理成功、占用失败后重试、危险路径与错误数据根 ID 拒绝。
- 恢复副本内容边界、最多一份、三次成功启动加七天保留条件和手动删除。
- 数据盘离线时只允许重试、定位有效目录或退出，不创建数据库。
- 设置页会话、CSRF、桌面模式限制、空间展示和重启迁移状态。
- 升级安装保留路径；静默和默认卸载保留数据；明确删除仅作用于验证后的精确目录。
- `APP_VERSION`、EXE、安装器和文件名统一为 `1.0.0`。
- 完整 pytest、Ruff、`git diff --check`、源码冒烟、打包桌面冒烟和安装/升级/卸载人工检查。

## 发布验收

在一台已有 `0.1.0` 数据的电脑上覆盖安装 v1.0.0，迁移到 D 盘并验证角色、分组、授权、钱包流水和同步。再从 D 盘迁移到另一个测试卷，确认原目录清理逻辑与盘符无关。临时卸载或断开数据盘时，程序必须拒绝创建空数据库。

验证默认卸载后重装能自动接回数据；验证明确删除时仅删除对话框中显示且带有效标记的数据根。最后在另一台干净电脑上安装，选择独立目录并完成首次授权，确认两台电脑的数据互不影响。

## Git 与交付

数据库、密钥、日志、WebView 用户数据、恢复副本、构建输出和安装包继续被 Git 忽略。远端仓库只包含源码、测试、构建配置和文档。

实现完成且验证通过后生成 v1.0.0 安装包及 SHA-256。是否提交实现、合并、推送、创建 `v1.0.0` 标签和 GitHub Release，仍由用户在完成审查后决定。

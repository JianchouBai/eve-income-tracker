# C 海军 LP 收入统计设计

日期：2026-10-18

状态：实现完成，已通过模拟测试和界面检查；真实 ESI 接入验收尚未执行。

## 目标和统计范围

为现有 EVE 收益统计器接入加达里海军 LP 收入，填充收益汇总、来源类型、角色分项和逐日账本中的 LP 占位。用户指定的军团项目名称为 `LP对账-C海军`。它记录累计个人贡献，领取项目奖励后不会减少。

统计来源是角色在指定军团项目中的累计贡献，不是个人 LP 钱包余额，也不是军团总进度。只统计该项目覆盖的 C 海军 LP；其他 LP、LP 折算 ISK、自动领取奖励、军团全员贡献统计均不在本期范围内。继续使用现有手动同步、角色组和角色筛选方式。

用户说明项目贡献记录税前 LP，并要求按 5% 扣除后计入收益。这里的 5% 是应用的结算扣率，不从游戏内 100% LP 上缴税率推导。应用展示按比例计算的税后 LP，不将它解释为角色个人钱包余额或已领取奖励。

成功标准：每个角色第一次成功读取建立独立基线，后续只将累计贡献的新增差额记为收入，乘以 0.95 后汇总到成功读取当天的北京时间日期。多次同步、失败重试和应用重启均不重复或漏写已经观察到的新增量；无法覆盖的区间明确显示状态。

## 方案选择

采用指定项目的个人累计贡献做差。它符合用户已确认的游戏内读数行为，并能够区分角色，不受领取项目奖励影响。

个人 LP 余额做差会混入消费影响，在 100% 上缴的场景下也不能反映产出，因此不采用。读取军团全员贡献需要额外的游戏内职位，超出当前按角色授权的用途，也不采用。

## 项目识别和绑定

1. 查询角色当前所在的玩家军团，使用该角色自己的项目读取授权列出军团项目，完整处理游标分页。
2. 首次绑定时按名称 `LP对账-C海军` 精确匹配，再读取详情验证项目类型和来源。项目必须为 `earn_loyalty_point`，且配置中的 LP 发放军团只有加达里海军，ID 为 `1000035`。
3. 来源为空、覆盖全部 LP 或包含其他发放军团时，不能从个人总贡献中拆分 C 海军 LP，显示“项目未限定 C 海军 LP”，不记账。
4. 首次绑定优先检查活跃项目；只有唯一有效活跃匹配时自动绑定。没有活跃匹配时，只有唯一有效历史匹配才可绑定并建立基线。零个匹配显示“未找到 LP 对账项目”；同一优先级有多个有效同名项目时显示“找到多个同名项目，无法确定统计来源”，不猜测项目。
5. 绑定键包含玩家军团 ID 和项目 UUID；名称只用于首次定位及显示。项目改名后继续按原 ID 读取，但仍校验类型、来源和计数口径。
6. 已绑定项目结束后继续尝试读取个人最终贡献。发现结束状态并不代表该角色的最终读数已经入账，只有成功取得读数并完成事务后才记录已读取尾账。
7. 列表请求使用 `state=All`；不能因默认只返回活跃项目而漏掉完成、关闭、过期的项目。已知项目即使不出现在列表中，也应尝试直接读取详情和个人贡献。
8. 删除后重建的同名项目是新项目。旧项目仍保留历史和基线；新 ID 独立建立基线，不将不同项目的累计值相减。存在旧项目未取回尾账时保留缺口提示。

每个玩家军团同一时刻只选择一个项目作为本期收入来源，不扫描并累加其他 LP 项目。角色换军团后使用新的军团和项目键；只有旧权限仍允许读取时才补取旧项目尾账，否则提示旧来源无法继续读取，不承诺补齐这段收入。

项目配置中的贡献倍率必须确认兼容“1 贡献单位等于 1 LP”。首期只接受未配置倍率或明确为 1 的设置；其他倍率显示“项目贡献单位不受支持”，不自行折算。个人贡献上限、项目总目标和项目状态用于提示可能的统计缺口。项目封顶或停止接受贡献后实际产生的 LP 无法通过此来源恢复。

## 授权和 ESI 请求

新授权请求同时包含以下两个只读 scope，继续使用现有 PKCE 和回调地址：

```text
esi-wallet.read_character_wallet.v1
esi-corporations.read_projects.v1
```

维护者先在现有 EVE Developers 应用中启用项目 scope，保持原 Client ID。程序再更新授权请求；已授权角色逐个重新授权后才能取得新增权限。旧 refresh token 不会自动扩大权限。无需添加个人 LP 余额、军团钱包或读取全员贡献的权限，也无需引入 Client Secret。

在 JWT 验证后保存角色实际获得的 scope。钱包 scope 仍是现有登录的基本条件，项目 scope 是 LP 能力条件：缺少它只影响 LP，不将角色整体标记为授权失效。升级前没有保存 scope 的角色可在下一次成功刷新并验证令牌后更新能力状态，不能仅凭空的迁移默认值认定钱包不可用。

项目请求使用下列接口，个人贡献请求中的角色 ID 必须与令牌身份一致：

```text
GET /corporations/{corporation_id}/projects
GET /corporations/{corporation_id}/projects/{project_id}
GET /corporations/{corporation_id}/projects/{project_id}/contribution/{character_id}
```

采用现有兼容日期 `2026-05-19`，无需为了本功能整体推进兼容日期。个人贡献取非负整数 `contributed`。可选的 `last_modified` 只作为观察元数据，不能据此拆分完整的 LP 产出时间。

请求沿用 User-Agent、安全错误转换和有限重试。项目列表使用游标分页，不能套用钱包的 `X-Pages` 分页逻辑。尊重服务端缓存与限流；缓存未变化不产生新收入。若使用条件请求，只有存在对应的有效本地快照才能接受 304。API 错误不转换为数值零。

## 收入计算和时间归属

对每个 `(character_id, corporation_id, project_id)` 单独维护基线：

```text
gross_lp = current_contributed - previous_contributed
deduction_lp = gross_lp × Decimal("0.05")
net_lp = gross_lp - deduction_lp
```

例如累计贡献从 1,000,000 增长到 1,200,000，记录税前 200,000 LP、扣除 10,000 LP、税后 190,000 LP。应用内部使用整数及 Decimal，持久化十进制文本，经 API 返回十进制字符串，不用二进制浮点计算或逐次向下取整。展示最多两位小数；内部值保持精确。比例结果不保证还原游戏逐笔扣除时的取整。

`observed_at` 取成功取得并校验本次个人贡献响应的 UTC 时间，收入日期为它转换到 `Asia/Shanghai` 后的日期。即使事务提交跨越午夜，也保留该观察时间，不按提交时刻重新归日。中断数日后新增差额全部计入此次同步日，不向之前日期摊分。不同角色使用各自的成功观察时间。

| 观察结果 | 入账和基线处理 |
| --- | --- |
| 没有历史基线 | 保存首个快照并建立基线，不将已有累计贡献导入当天收入 |
| 本次值大于基线 | 保存前后读数及正差额，按本笔扣率入账，推进基线 |
| 本次值等于基线 | 记录成功观察，无新增收入 |
| 本次值小于基线 | 记录异常观察，不写负收入、不降低基线 |
| 请求失败、响应非法、权限不足 | 保留已确认的基线和收入，单独更新失败状态 |
| 项目变更类型、来源或计数单位 | 暂停该来源记账，保留历史并提示配置不兼容 |

项目配置恢复兼容后，不能把暂停期间增长的总贡献直接计为 C 海军收入。首次恢复读取建立新的基线段，记录统计缺口并保留旧段历史，后续才继续计算新增量。单纯改名且配置口径未变时不重建基线。读数降低本身也不触发自动重建，仍按异常规则保留旧基线。

首次 LP 基线时间独立于角色原有钱包统计起点；重新授权不重置钱包起点或已经存在的 LP 基线。更换项目不使用新项目的创建时间推断其历史贡献属于哪个已统计区间。

本期扣率默认固定为 5%，不增加税率设置界面。每笔记录仍保存使用的扣率，以便将来调整规则时只影响新记录。报表始终汇总已保存的历史税后值，不按当前扣率重算过去收入。

## 存储和迁移

数据库 schema 从 2 升级为 3，沿用现有升级前备份、事务迁移和恢复流程。版本 1 先完成现有迁移，再应用版本 3 变更；新数据库直接创建最新结构。不改写旧角色的分组、启停、钱包起点和钱包流水。

为角色增加已验证 scope 的持久化字段，默认空集合。LP 持久化职责按以下边界划分，具体 SQL 由实现计划细化：

| 数据 | 必需内容和约束 |
| --- | --- |
| 项目绑定 | 玩家军团 ID、唯一选中项目 ID、名称、C 海军来源和配置摘要、项目状态、绑定时间 |
| 角色追踪状态 | 角色／军团／项目联合唯一键、当前基线段标识、首次基线时间、当前已接受贡献值、最后成功观察时间、LP 状态和安全错误码 |
| 观察快照 | 角色和项目身份、基线段标识、贡献整数、观察时间、可选修改时间、是否被接受及异常类型；不包含授权令牌 |
| LP 入账明细 | 对应快照、前后贡献值、区间起止观察时间、本次税前差额、扣率、扣除 LP、税后 LP；同一快照至多一笔入账 |

更新基线、保存被接受快照和新增入账明细必须在同一事务中完成。失败全部回滚。事务内验证当前基线没有被其他请求推进；同一角色的授权刷新和同步串行，避免重叠请求导致重复入账或刷新令牌竞争。数据库约束作为第二道防线。

累计读数使用非负整数，超出 SQLite 支持范围时拒绝并保留原数据。项目 UUID 使用独立字符串字段，不混入当前只接受正整数的 HTTP 资源 ID 校验。

更新 `database_lifecycle.py` 的最新 schema 识别、导入检查及相关验证，防止桌面启动时拒绝合法的新数据库。数据目录迁移、备份、导入和授权重置应保留 LP 业务表与基线；跨安全边界导入仍按现有规则清除授权能力，重新授权后继续使用已保存的 LP 历史。高于支持版本的数据库仍明确拒绝。

## 同步和报表接入

保持一个手动同步入口，按钮文案调整为“同步收益”。每个角色共用一次有效授权刷新，然后分别执行钱包与 LP 同步。两类数据独立提交：钱包成功但 LP 缺权限、缺项目或请求失败时保留钱包成果；LP 成功但钱包失败时也保留 LP 成果。真正的令牌撤销或失效可以同时阻断两者。

现有同步结果增加 LP 结果，包含状态、完成时间、是否刚建立基线、本次税前和税后新增 LP、安全错误码。保留现有钱包结果字段的含义，前端分别展示结果，不把 LP 缺权限解释为钱包令牌失效。

报表沿用现有角色组、角色启停、显式角色筛选、日期范围和最多 366 天限制。LP 收入绑定角色和项目，组统计遵循现有按当前成员归集的方式；不另建一套组历史口径。每月逐日账本仍独立于顶部周期。

汇总与每个日／角色行增加独立的 `lp` 数据，包含税前、扣除、税后三个十进制字符串；数值与 ISK 字段不相加。来源类型区显示独立的“C 海军 LP”读数。主 LP 读数使用税后值，清楚标注“按同步日统计，扣除 5%”。原钱包流水明细仍显示 ISK，不伪造钱包交易来承载 LP。

LP 数值与覆盖状态分开返回：已确认的收入继续显示；如果部分选中角色待授权、无基线或同步异常，则附“统计不完整”提示。没有任何有效覆盖时显示 `—`，不能用 `0 LP` 代替未知。首次基线之前的日期不声称已确认零收入；有覆盖但没有新增的日期显示零。周期跨越基线时保留已知合计并提示起算时间。

角色状态使用面向用户的说明，例如“LP 待授权”“LP 基线已建立”“LP 已同步”“未找到 LP 对账项目”“LP 读数异常，已保留上次记录”。同步失败不会清空已有 LP。项目结束、个人上限或总目标达到上限时提示来源可能停止记录，不推算未观察到的收入。

## 验证要求

实现时使用模拟 ESI 响应验证规则；不会把用户私有令牌或真实项目数据写入仓库。重点覆盖：

- scope 请求、JWT 验证和持久化；钱包旧授权仍可用；补授权不改变钱包起点或 LP 基线。
- 唯一项目绑定、名称变更、同名新 ID、错误类型、混合 LP 来源、非 1 倍率、项目列表多页和结束项目尾账。
- 首次建立基线、大于／等于／小于基线、连续失败后恢复、重复请求、并发、事务失败和重启后的精确一次入账。
- UTC 16:00 北京时间日界、响应与事务提交跨日、多日未同步，以及同步次数不影响税后合计。
- 钱包与 LP 各自成功或失败的组合、角色组及显式角色筛选、历史保留、未知值与零值区别、统计不完整提示。
- 版本 1／2 升级到 3、新数据库、升级幂等、失败恢复、未来版本拒绝、桌面 schema 识别及迁移和导入保留 LP 表。

实现完成后运行相关 pytest、Ruff、`git diff --check` 和既有启动冒烟检查。此次文档交付不改变运行时代码，也不构建安装包或发布版本。

真实接入时，补齐权限后读取 `LP对账-C海军` 的项目 ID 与配置；以一个角色建立基线，获取一笔已知数量 LP 后再次同步，再领取项目奖励并复读，确认 ESI 贡献单位、税前口径与累计不回退的行为。该验证是宣称真实 ESI 接入成功的条件；未完成时只报告模拟验证结果。
